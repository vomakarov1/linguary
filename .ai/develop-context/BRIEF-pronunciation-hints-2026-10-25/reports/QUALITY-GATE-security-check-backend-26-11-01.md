## Checks covered

- Чтение словаря и уведомлений: `source.py:29-30,69-83` и `pronunciation_notices.py:19-28` используют фиксированные имена ресурсов; проверяются версия, манифест и контрольные суммы. Входной запрос не задаёт путь к файлу.
- HTTP: `routes/result.py:22-29` отдаёт только фиксированные лицензионные сведения как `text/plain`; маршрут не принимает идентификаторы или URL и не выполняет сетевых запросов.
- HTML: изменённый шаблон результата использует Jinja autoescape. Проверено для HTML-шаблонов через `templates.env.autoescape(...)` — включено. Значения IPA, цитаты и атрибуция выводятся в экранируемых текстовых/атрибутных контекстах.
- EPUB/XML: `writer.py:257-268` добавляет текст через `lxml` `.text`, ссылки строит из зарезервированных внутренних имён ресурсов; пользовательские строки не интерпретируются как разметка. Данные о происхождении записей сериализуются через `json.dumps`.
- Происхождение данных: `PronunciationEvidence` требует точный источник и формат URI для `lexicon_form`; отбор принимает только проверенный вариант и локально найденную точную форму.

### Повторная проверка `d51945a..bac3fd0`

- `linguary.js:58-75,234-264` получает фрагмент по `form.action` с учётными данными только для того же источника; перед вставкой сверяет единственный корневой блок и его `id` с текущим. Это структурная проверка, а защиту разметки обеспечивает серверный шаблон.
- `result_block.html:18` формирует `data-block-id` в HTML-атрибуте. Jinja autoescape для `.html` включён; в изменённом шаблоне нет `|safe`/`Markup`.

- Фрагмент приходит от обработчика с того же источника (`result.py:83-100,108-126`), который формирует его фиксированным Jinja-шаблоном с проверенным автоэкранированием.

### Повторная проверка `bac3fd0..2f3bf9c`

- `result.py:83-98,176-213` принимает `block_id` как повторяемые query-параметры, затем сопоставляет их только с группами одного снимка книги. Идентификаторы чужой книги не дают доступ к её блокам; неизвестный ID приводит к 404. При отражении неизвестного значения JSON сериализует его как данные, а HTML-обработчик выводит через автоэкранируемый `error.html`.
- `result_blocks.html` включает тот же фиксированный `result_block.html`; все динамические значения остаются в HTML-тексте/атрибутах с автоэкранированием. В `linguary.js:242-265` список ID добавляется через `URLSearchParams`, а ответ разбирается как шаблон; проверяется корневой контейнер и что дочерние элементы — только блоки результата. Вставляемые поля не конкатенируются в HTML.

### Повторная проверка `2f3bf9c..2253338`

- `result.py:83-91` отклоняет запрос до чтения книги, если передано больше 128 значений или длина любого ID больше 512 символов; ответ не отражает переданные значения.
- `result.py:189-195` теперь сравнивает ID блоков каждой группы с множеством запроса, поэтому обход линеен по числу блоков книги и числу переданных ID, без прежнего повторного прохода по всему списку для каждой группы.
- `linguary.js:234-245` отправляет ID последовательными пакетами не более 128 значений. Значения кодируются через `URLSearchParams`.
- Сопоставление остаётся ограничено снимком запрошенной книги; `block_id` не попадает в SQL, HTML или селектор DOM. HTML-фрагмент формирует тот же автоэкранируемый шаблон.

## Статус прежней низкоприоритетной находки

Закрыта: пакет ограничен 128 ID по 512 символов каждый, а серверное сопоставление больше не имеет сложности `O(число групп × число ID)`.

## Остаточные ограничения

- Проверен код ветки относительно `main`; настройки и защита развёрнутого экземпляра отдельно не проверялись.
- Отдельные поверхности приложения и общая модель аутентификации за пределами изменений P8–P11 не входили в проверку.
- `template.innerHTML` остаётся чувствительной точкой: безопасность зависит от сохранения автоэкранирования и запрета необработанного пользовательского HTML в шаблоне. В проверенной дельте этот инвариант соблюдён.
- Настройки ограничения размера строки запроса на рабочем сервере/прокси не проверялись. В приложении обработчик ограничивает число ID и длину каждого значения; разбор исходной строки запроса до вызова обработчика остаётся на стороне ASGI-сервера.
