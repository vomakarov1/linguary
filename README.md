# Linguary

Локальное приложение для обработки художественных книг EPUB через LLM: перевод en→ru, словарные
подсказки и языковые заметки для читателя, изучающего язык. Приложение запускается на машине
пользователя, хранит данные в SQLite и обращается к внешнему LLM-провайдеру по HTTP.

## Требования

- Python 3.13
- [uv](https://docs.astral.sh/uv/) для управления зависимостями и окружением

## Установка

```sh
uv sync
```

Команда создаёт виртуальное окружение `.venv`, ставит зависимости по `uv.lock` и подключает пакет
`linguary` в редактируемом режиме.

## Тесты

```sh
uv run pytest -v
```

Соглашения по тестам, разбивка по директориям и запуск отдельных наборов описаны в playbook
тестирования проекта.

## Структура

Модульный монолит с Clean Architecture, направление зависимостей — только внутрь:
`domain` ← `application` ← `adapters` / `web` / `cli`.

| Пакет                  | Содержимое                                                              |
| ---------------------- | ----------------------------------------------------------------------- |
| `linguary.domain`      | Предметные сущности и инварианты; чистый Python без сторонних библиотек  |
| `linguary.application` | Сценарии и порты (Protocol/ABC), транзакционные границы                  |
| `linguary.adapters`    | Реализации портов: `db`, `epub`, `llm`, `config`, `validation`, `runtime` |
| `linguary.composition` | Состав зависимостей: единственное место, где известны конкретные адаптеры |
| `linguary.web`         | HTTP-слой: FastAPI и серверные шаблоны Jinja2                            |
| `linguary.cli`         | Точка входа командной строки                                             |

Границы слоёв закреплены архитектурными тестами в `tests/architecture`: они разбирают импорты
модулей `domain` и `application` и запрещают зависимости на внешние библиотеки, инфраструктурные
модули стандартной библиотеки и внешние слои.

## Запуск

```sh
uv run python -m linguary.cli serve
```

Команда поднимает Web UI на адресе из секции `[server]` локальной конфигурации — по умолчанию
`http://127.0.0.1:8000`. Приложение само приводит базу к текущей схеме, создаёт каталог данных
и выполняет фоновые задачи в своём процессе, поэтому отдельный воркер для обычной работы
запускать не нужно.

Сервер по умолчанию доступен только с этой машины: приложение хранит ключ провайдера и полный
текст книг. Открывать его на другом интерфейсе стоит только осознанно, изменив `[server] host`:
по этому же адресу приложение ограничивает имена, с которыми принимает запросы.

Запускать приложение нужно из исходного дерева репозитория — в том числе через редактируемую
установку `uv sync`. Миграции лежат в каталоге `alembic/` рядом с пакетом, а не внутри него,
поэтому собранный отдельно wheel их не содержит.

### Запуск через Docker

Приложение можно запустить в контейнере с помощью Docker Compose:

```sh
LINGUARY_LLM_API_KEY="ваш_api_ключ" docker compose up --build
```

Web UI будет доступен по адресу `http://localhost:8000`. Каталог данных и база SQLite сохраняются в томе `linguary_data` (путь `/data` в контейнере).

Также возможен запуск через Docker напрямую:

```sh
docker build -t linguary .
docker run -d \
  -p 127.0.0.1:8000:8000 \
  -e LINGUARY_LLM_API_KEY="ваш_api_ключ" \
  -e LINGUARY_LLM_MODEL="gpt-4o-mini" \
  -v linguary_data:/data \
  linguary
```

## Конфигурация

Пути к локальным данным, адрес и ключ LLM-провайдера, лимиты обработки читаются из окружения или
локального файла настроек (`~/.linguary/config.toml`) и не хранятся в коде репозитория. Секции
настроек: `[llm]` — провайдер, модель, ключ и лимиты; `[checks]` — пороги автоматических проверок;
`[storage]` — каталог данных и файл базы; `[server]` — адрес и порт локального Web UI;
`[worker]` — параллелизм фоновых задач. Любое значение перекрывается переменной окружения вида
`LINGUARY_<СЕКЦИЯ>_<НАСТРОЙКА>`.

Скорость обработки задают две настройки:

- `[worker] concurrency` (`LINGUARY_WORKER_CONCURRENCY`) — сколько задач выполняется
  одновременно, по умолчанию одна. Ускоряет обработку глав, которые независимы друг от друга.
  Анализ глав от неё не ускоряется: главы анализируются строго по очереди, потому что каждая
  видит кандидатов глоссария предыдущих;
- `[llm] requests_per_minute` (`LINGUARY_LLM_REQUESTS_PER_MINUTE`) — сколько запросов в минуту
  приложение отправляет провайдеру всеми воркерами вместе. По умолчанию не задана, и частота
  не ограничивается. Задайте её по тарифу провайдера, если при `concurrency` больше единицы он
  начинает отвечать отказом `429`. Паузу, которую провайдер сам называет заголовком
  `Retry-After` в ответах `429` и `503`, приложение выдерживает перед повтором в любом случае.

```toml
[worker]
concurrency = 4

[llm]
requests_per_minute = 60
```

Пока идёт анализ или обработка, карточка книги показывает все выполняющиеся главы и примерное
оставшееся время. Оценка грубая: медианная длительность вызова модели для этой книги,
умноженная на оставшуюся работу и делённая на параллелизм; до первого завершённого вызова её нет.

Текущее состояние конфигурации приложение показывает само — на экране конфигурации и окружения
(`GET /system/config`): настроена ли LLM, какая модель активна, доступна ли внешняя проверка
EPUBCheck и где лежат данные. Ключ провайдера в ответ не попадает.
